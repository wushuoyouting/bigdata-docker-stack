# Iceberg 原理

> **一句话结论**：Iceberg 用「快照加 manifest 树」管理文件。每次提交生成一个新快照，旧快照保留支撑时间旅行。引擎通过原子替换元数据文件实现并发读写的隔离。

> **本文解决什么**：讲清 Iceberg 的数据布局、元数据层级、提交机制与更新语义。

> **适用谁**：已选定 Iceberg，准备理解其行为边界的人。

> **读完能做什么**：解释 COW 与 MOR 的差别，判断一次写入会产生哪些文件，理解并发与时间旅行的代价。

---

## 一、整体架构

Iceberg 分三层。上层是引擎，中层是表格式，下层是对象存储。

```
引擎：Spark / Flink / Trino / Hive
        ↓ SQL 与只读快照
表格式：Iceberg 元数据 + manifest + 数据文件
        ↓ S3 API
对象存储：MinIO 的 s3://lakehouse/iceberg/
```

Iceberg 本体是 jar。它挂进引擎的 classpath 才工作。

---

## 二、数据文件布局

一张 Iceberg 表在 MinIO 上是一个目录。目录结构是固定的。

```
s3://lakehouse/iceberg/db/t1/
├── metadata/
│   ├── v1.metadata.json
│   ├── v2.metadata.json
│   ├── snap-123-1.avro
│   └── 2f7c...-m0.avro
└── data/
    ├── dt=2026-11-17/
    │   └── 00000-1-abc.parquet
    └── dt=2026-11-18/
        └── 00001-2-def.parquet
```

各目录职责如下。

| 目录 | 内容 |
| --- | --- |
| metadata | 元数据文件、快照清单、manifest 文件 |
| data | 实际数据文件，常用 Parquet 或 ORC |

文件名带唯一编号，写入不覆盖旧文件。这是快照隔离的基础。

## 三、元数据三层树

Iceberg 的元数据分三层。这是它与其它表格式最显著的区别。

```
metadata.json（表级）
    └── snapshot（快照）
            └── manifest list（快照清单，Avro）
                    └── manifest file（文件清单，Avro）
                            └── data file（数据文件，Parquet）
```

### 3.1 metadata.json

表级元数据。记录 schema、分区规则、属性、当前快照指针。

每次提交生成新版本，如 v1、v2。文件名递增，旧版本保留。

### 3.2 snapshot

快照是某一时刻表的完整状态。每次成功提交产生一个快照。

快照记录本次提交的时间、摘要、以及 manifest list 的位置。

### 3.3 manifest list

一个快照对应一个 manifest list。它列出该快照引用的全部 manifest 文件。

清单里带分区范围与文件数，查询可据此跳过无关文件。

### 3.4 manifest file

manifest 记录数据文件的明细。包含路径、大小、行数、列级统计、分区值。

列级统计能做谓词下推，减少要读的文件。

## 四、提交与并发

### 4.1 乐观并发控制

Iceberg 不用锁表。写入流程分四步。

① 读取当前 metadata.json，记下版本号。

② 写新数据文件与 manifest 文件。

③ 生成新 metadata.json，指向新快照。

④ 用原子写把 catalog 的指针换到新 metadata.json。

第 ④ 步失败时，写入方重试。它重读最新版本，再走一遍流程。

### 4.2 隔离级别

读者加载表时锁定一个快照。锁定期内不受新提交影响。

读者只在刷新表时才看到新快照。这叫快照隔离。

写者之间靠版本号冲突检测，保证串行化提交。

### 4.3 catalog 的职责

catalog 负责把表名映射到当前 metadata.json 的位置。

catalog 本身不存数据文件。它只存一个指针。

常用实现有 rest、hms、glue、hadoop。本机学习用 hadoop 类型即可。

## 五、更新机制

Iceberg 支持行级更新，有两种写模式。

### 5.1 COW

COW 是写时复制。更新一行时，重写整份数据文件。

优点：读路径简单，查询快。

缺点：更新集中时写放大明显。

### 5.2 MOR

MOR 是读时合并。更新写入独立的 delete 文件，读时再合并。

优点：写入快，适合高频小批量更新。

缺点：读时要合并，查询变慢，需要后台重写。

### 5.3 两种模式对比

| 项 | COW | MOR |
| --- | --- | --- |
| 写放大 | 大 | 小 |
| 读延迟 | 低 | 高 |
| 适合 | 批量更新、读多写少 | 高频更新、近实时写入 |
| 后台维护 | 压力小 | 需定期合并 delete 文件 |

## 六、关键能力如何落地

### 6.1 时间旅行

按快照号或时间戳读旧快照，只需把表的指针指向历史 metadata.json。

旧数据文件不被删除时，历史快照随时可读。

### 6.2 schema 演进

加列只改 metadata.json，不碰数据文件。

旧文件缺的列读成 null。改列名、改类型同理在元数据层完成。

### 6.3 分区演进

分区规则也存元数据。改分区只影响新写入的数据。

旧数据保留原布局，查询时按各快照的分区规则分别解析。

### 6.4 隐藏分区

用户写查询不必知道分区列名。引擎从数据算出分区值。

这避免了手写分区条件写错的问题。

---

## 七、代价与边界

① 每次提交都产生元数据文件。高频小批量写会产生大量文件。

② MOR 模式依赖后台合并。合并不及时会让查询持续变慢。

③ Iceberg 没有原生主键表。行级 upsert 靠 MERGE INTO 加唯一键约束实现。

④ 快照过期要定期清理，否则对象存储里旧文件不断累积。

## 八、本机 Quickstart 部件分工

本机采用 Apache 官方 Flink Quickstart 编排。五个部件各司其职。

| 部件 | 镜像 | 职责 |
| --- | --- | --- |
| jobmanager | 本地构建 | 调度 Flink 作业，提供 SQL 客户端 |
| taskmanager | 本地构建 | 执行 Flink 作业任务 |
| iceberg-rest | apache/iceberg-rest-fixture | 提供 REST Catalog 服务 |
| object-store | rustfs/rustfs:1.0.0 | 存放数据文件与元数据文件 |
| create-bucket | rustfs/rustfs:1.0.0 | 初始化 warehouse 存储桶 |

Flink 通过 REST 协议访问 Catalog。数据文件通过 S3 兼容接口写入 rustfs。

官方编排的容器都在 iceberg_net 网络内，容器间用服务名互访。这与本机公共网络 whd-net 是两套网络。接入 whd-net 时须按 172.30.0.4 固定地址，详见安装教程。

## 九、本篇小结

① Iceberg 的元数据是三层树：metadata.json、manifest list、manifest。

② 提交靠原子替换元数据指针，冲突时重试，不锁表。

③ COW 写放大但读快，MOR 写快但读时要合并。

④ 时间旅行、schema 演进、分区演进都落在元数据层。

⑤ 没有原生主键，upsert 靠 MERGE INTO 实现。

⑥ 本机 Quickstart 用 REST Catalog 加 rustfs，引擎是 Flink。
