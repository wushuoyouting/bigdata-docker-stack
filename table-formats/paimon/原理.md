# Paimon 原理

> **一句话结论**：Paimon 用「LSM 加 bucket 加 snapshot」支撑流式更新。写入先进内存，再落磁盘分层，后台 compaction 合并。提交绑定 Flink checkpoint，查一次快照就是一次一致读。

> **本文解决什么**：讲清 Paimon 的 LSM 结构、bucket、快照提交与 changelog。
>
> **适用谁**：已选定 Paimon，用 Flink 做流式入湖的人。
>
> **读完能做什么**：理解主键表为何能高吞吐 upsert，解释 checkpoint 与数据可见性的关系，判断 bucket 数怎么设。

---

## 一、整体架构

Paimon 分三层。上层是引擎，中层是表格式，下层是对象存储。

```
引擎：Flink / Spark / Trino / Doris
        ↓ SQL 读写
表格式：LSM 分层 + bucket + snapshot + manifest
        ↓ S3 API
对象存储：MinIO 的 s3://lakehouse/paimon/
```

Paimon 本体是 jar。本机用 paimon-flink-1.20-1.3.1.jar。

---

## 二、表类型

Paimon 有两种表。选型先定表类型。

| 表类型 | 主键 | 更新方式 | 用途 |
| --- | --- | --- | --- |
| 主键表 | 有 | upsert 或 append | CDC 同步、实时更新 |
| append-only 表 | 无 | 只追加 | 日志、事件流 |

主键表是 Paimon 的招牌能力。它支持高吞吐的行级更新。

---

## 三、数据文件布局

一张主键表在 MinIO 上的目录结构如下。

```
s3://lakehouse/paimon/game_db/t_order/
├── schema/
│   └── schema-0
├── snapshot/
│   ├── 1
│   └── 2
├── manifest/
│   ├── manifest-list-xxx-1
│   └── manifest-yyy-1
└── bucket-0/
    └── sst/
        ├── data-aaa.parquet
        └── data-bbb.parquet
```

关键目录说明。

| 目录 | 内容 |
| --- | --- |
| schema | schema 演进历史 |
| snapshot | 快照文件，记录变更的文件清单 |
| manifest | 文件清单，记录快照涉及的数据文件 |
| bucket-N | 按 bucket 分的数据目录，存 LSM 分层文件 |

## 四、LSM 分层结构

### 4.1 写入流程

Paimon 采用 LSM 树结构。写入分四步。

① 记录先进内存缓冲。

② 缓冲写满后，刷成有序的 level-0 文件。

③ level-0 文件累积到阈值，后台 compaction 合并进更高层。

④ 每层文件保持键有序且层内不重叠。

### 4.2 为什么适合更新

LSM 把随机写转成顺序写。更新不必原地改文件。

同一主键的新值写成新记录。读取时按 seq 取最新版本。

这带来高写入吞吐，代价是读时要合并多层。

### 4.3 compaction 的作用

① 合并同键的多个版本，只留最新。

② 减少文件数，降低读放大。

③ 清理被标记删除的记录。

compaction 不及时，查询变慢且小文件暴涨。

## 五、bucket 机制

### 5.1 什么是 bucket

bucket 是数据分片的单位。主键按哈希落到固定 bucket。

每个 bucket 是独立的 LSM 树，有自己的数据目录。

### 5.2 为什么需要 bucket

① 并行度。不同 bucket 可并行读写。

② 定位。按主键查询能直接算出 bucket，避免全表扫描。

③ 局部性。同键的记录永远在同一 bucket，compaction 范围可控。

### 5.3 bucket 数量怎么定

bucket 数决定并行度与文件粒度。设太小会形成大文件与写入瓶颈。

设太多会产生大量小文件，元数据膨胀。

经验做法：按单 bucket 目标数据量估算，再取 2 的幂。

本机 ADS 结果表只有几十行，用 bucket=1 即可。

## 六、快照与提交

### 6.1 提交绑定 checkpoint

Paimon 的写任务依赖 Flink checkpoint 提交。

一次 checkpoint 完成，才生成一个新快照，数据才对外可见。

不开 checkpoint，作业在跑但湖里没有可读数据。

### 6.2 快照内容

每个快照记录本轮新增与删除的数据文件。

快照按其编号命名，存在 snapshot 目录。

### 6.3 两阶段提交

① checkpoint 开始，写任务把数据刷成文件，暂不提交。

② checkpoint 完成，协调器通知写任务提交。

③ 写任务生成快照文件，完成可见。

失败时未提交的快照不生效，读方看不到中间态。

---

## 七、changelog

主键表能产出 changelog。每次更新生成一条 before 与 after 记录。

下游可订阅 changelog 做增量处理，不必对比两份快照。

这支撑「湖上继续流」的链路，是流批一体的一环。

---

## 八、时间旅行与增量读

### 8.1 时间旅行

按快照号读历史版本。旧文件未被清理时可读。

### 8.2 增量读

指定起始快照号，只读该快照之后的变化。

增量读配合 changelog，支撑下游的增量消费。

---

## 九、catalog 与元数据

catalog 负责定位表，即把表名映射到元数据位置。Paimon 支持三种常用 catalog。

| 类型 | 全称 | 元数据存在哪 | 是否需独立服务 | 典型场景 |
| --- | --- | --- | --- | --- |
| filesystem | 文件系统 | warehouse 目录内 | 否 | 本机学习、单集群共享 |
| hms | Hive Metastore | Hive Metastore 服务 | 是 | 多引擎共享、需统一权限 |
| jdbc | JDBC 数据库 | MySQL 或 PostgreSQL | 是 | 需事务与审计 |

### 9.1 hms 是什么

hms 是 Hive Metastore 的缩写。它是 Hive 的元数据服务，独立跑在一个 JVM 里。

它存表名、字段、分区、存储位置。Spark、Flink、Hive、Doris 都可向它注册和查询表。

选 hms 时，多引擎通过同一个服务看到同一张表，不必约定 warehouse 路径一致。

代价是要额外部署并维护一个服务。

### 9.2 filesystem catalog

元数据就是 warehouse 目录下的文件。本机采用此类型。

Flink 与 Doris 认同一路径即可共享。

不必起 Hive Metastore，零额外服务。

代价是没有托管权限与审计，演示场景够用。

### 9.3 jdbc catalog

元数据写进关系库，通过 JDBC 读写。常用 MySQL 或 PostgreSQL。

它提供事务与审计能力。

代价是要维护一个数据库。

### 9.4 三种怎么选

① 本机学习、单集群共享，选 filesystem。

② 多引擎要统一表注册与权限，选 hms。

③ 要元数据事务与审计，选 jdbc。

注意：hive metastore 的全称是 Hive Metastore，缩写 hms 或 HMS。文档里两种写法指同一服务。

## 十、代价与边界

① checkpoint 间隔决定可见延迟。间隔越大，数据可见越慢。

② bucket 数一旦定下，调整要重分布数据。

③ 主键表依赖 compaction，否则读放大持续累积。

④ filesystem catalog 没有统一权限审计，生产要换 hms 或 jdbc。

---

## 十一、本篇小结

① Paimon 用 LSM 加 bucket 支撑高吞吐主键更新。

② 写入先进内存，刷成 level-0 文件，再后台 compaction。

③ 提交绑定 Flink checkpoint，不开 checkpoint 就没有可见数据。

④ bucket 决定并行度与文件粒度，要按数据量预估。

⑤ 主键表能产出 changelog，支撑下游增量消费。
