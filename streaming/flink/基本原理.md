# Flink 基本原理

> **一句话结论**：Flink 是分布式流处理引擎。JobManager 调度，TaskManager 执行，Client 提交作业。Paimon 是表格式，不是服务。本机把前两个角色合进一个容器，Client 按需调用。

> **本文解决什么**：理解 Flink 为何分三类角色、Paimon 为何不起容器、本机单容器部署的依据。
>
> **适用谁**：准备安装 Flink，或想知道安装命令背后逻辑的用户。
>
> **读完能做什么**：判断某个组件该不该单独起容器，解释 checkpoint 与写湖的关系，理解 SQL Client 的两种运行模式。

## 一、三类角色

| 角色 | 英文名 | 职责 | 是否常驻 |
| --- | --- | --- | --- |
| 作业管理器 | JobManager | 接收作业、调度任务、协调 checkpoint、维护元数据 | 是 |
| 任务管理器 | TaskManager | 执行具体任务、上报心跳、管理槽位 | 是 |
| 客户端 | Client | 编译 SQL、生成作业图、提交作业、取回结果 | 否 |

**JobManager** 是集群的大脑。它把作业图拆成并行子任务，分配给 TaskManager。它记录作业状态，保存 checkpoint 元数据，处理故障恢复。Web UI 也跑在这里。

**TaskManager** 是集群的手脚。它按槽位运行子任务，定期心跳上报状态。数据流算子在 TaskManager 进程里执行。读写外部存储的连接器也在这里加载。

**Client** 只是一个工具。它把 SQL 或 jar 转成作业图，提交给 JobManager。提交完即退出。作业继续在集群里运行。所以 Client 不需要单独起一个容器长期运行。

> 本机把 JobManager 与 TaskManager 放进同一个容器。它们用 localhost 通信。Client 用 docker exec 从同一个容器里调用。镜像里已经带了 sql-client.sh 与 flink 命令。

## 二、为什么不把 Client 当服务

Flink 镜像自带 bin/sql-client.sh 与 bin/flink。这两个是命令行工具，不是守护进程。它们随用随起，执行完退出。

把 Client 做成常驻容器会带来三个问题。一是容器启动即退出，必须加 tty 保活。二是常驻进程不做事却占内存。三是 connector jar 要在额外容器里再挂一份，容易漏。

本机采用 docker exec 进集群容器调用。这样工具与集群共享镜像、共享 jar、共享网络配置。

> SQL Client 有两种执行方式。embedded 模式在客户端进程内启动一个迷你集群，用于语法调试。连接已有集群则通过 REST 地址提交作业。本机验收用 embedded 做只读查询。正式提交用 flink run。

## 三、槽位与并行度

**槽位** 是 TaskManager 的执行单元。一个 TaskManager 可有多个槽位。本机配置为 2。

**并行度** 是一个算子同时运行的实例数。并行度不能超过总槽位数。本机 parallelism.default 设为 2，与槽位数匹配。

| 概念 | 决定什么 | 本机取值 |
| --- | --- | --- |
| TaskManager 数 | 执行进程的个数 | 1 |
| 每 TM 槽位数 | 每个进程并行执行的能力 | 2 |
| 并行度 | 单个算子展开的实例数 | 2 |

> 槽位不是 CPU 核数。它是内存与线程的逻辑隔离单位。16G 机器上给 TM 限 1G 内存，槽位设 2，避免挤掉 Doris BE。

## 四、作业与数据流

一个 Flink SQL 作业会转成一张有向图。图上有三类节点：

1. **Source**：读取数据。例如 datagen 造数据，Doris connector 读表。
2. **Transform**：计算。例如过滤、聚合、关联。
3. **Sink**：写出数据。例如 blackhole 丢弃，Paimon connector 写湖。

有界源的作业会自己结束。datagen 设了 number-of-rows 时，数据造完作业变 FINISHED。无界源作业会一直 RUNNING，直到手动取消或出错。

> 判断作业成功不能只看状态。有界源 FINISHED 是正常终态。无界源 RUNNING 才正常。要看日志无异常、checkpoint 完成、目标端有文件。

## 五、状态与 checkpoint

**状态** 是算子在处理过程中保存的中间数据。聚合结果、窗口内容、去重集合都属于状态。

**checkpoint** 是状态的一致性快照。Flink 定期把状态写到持久化目录。作业失败时从最近的 checkpoint 恢复。

**Paimon 的提交绑定 checkpoint**。这是写湖链路最关键的一条。Paimon 表的数据文件在 checkpoint 完成时才会被提交，对读者可见。不开 checkpoint，会出现作业在跑、湖里没有文件的假故障。

| 配置 | 本机取值 | 原因 |
| --- | --- | --- |
| state.checkpoints.dir | file:///checkpoints | JM 与 TM 共用挂载目录 |
| execution.checkpointing.interval | 10s | 每 10 秒一次快照 |
| execution.checkpointing.mode | EXACTLY_ONCE | 保证恰好一次语义 |

> 独立安装阶段也配置 checkpoint，但不提交作业。checkpoints/ 目录此时为空。写湖时才会产生快照文件。

## 六、SQL 到作业的转换路径

① 用户提交 SQL 给 Client。
② Client 解析 SQL，校验表与字段。
③ Client 生成作业图，提交给 JobManager。
④ JobManager 分配任务给 TaskManager。
⑤ TaskManager 运行算子，读写外部存储。
⑥ 结果回传给 Client 展示，或写入 Sink。

SELECT 查询的结果通过 Client 取回显示。INSERT 作业的结果写入 Sink，Client 只返回作业 ID。这是两种 SQL 的本质区别。

## 七、为什么 Paimon 不是服务

Paimon 是一种表格式。它定义了数据文件、清单文件、快照文件的组织方式。它同时提供 Flink connector，让 Flink 能读写这种格式。

Paimon 没有独立进程。没有 RPC 端口。没有 Web UI。元数据存在 warehouse 目录里，本例是 MinIO 上的 s3://lakehouse/paimon。

| 组件 | 是否独立服务 | 角色 |
| --- | --- | --- |
| Flink | 是 | 计算引擎 |
| MinIO | 是 | 对象存储 |
| Doris | 是 | 分析型数据库 |
| Paimon | 否 | 表格式加 connector jar |

> 因为 Paimon 不是服务，所以不需要为它起容器。只需要在 Flink 与 Doris 两边都放上对应的 jar，并约定同一个 warehouse 路径。

## 八、单容器与分容器的取舍

| 维度 | 单容器 | 分容器 |
| --- | --- | --- |
| 容器数 | 1 | 1 JM 加 N TM |
| 角色隔离 | 无，共命运 | 有，独立重启 |
| 扩容 TM | 不支持 | 支持 |
| RPC 配置 | localhost | 服务名或 IP |
| 内存占用 | 低 | 高 |
| 适用场景 | 本机演示、开发 | 生产、多用户 |

**官方推荐分容器**。原因是生产环境需要故障隔离与弹性扩容。TaskManager 按需加到几十个。JobManager 独立重启不影响任务进程。

**本机选择单容器**。原因是 16G 内存要跑 Doris、MinIO、Superset 等多个组件。单容器省内存，配置简单。代价是不能单独扩 TM，一个角色挂掉整个容器结束。这个代价在演示环境可接受。

> 两种形态的 SQL 写法完全一致。区别只在部署与运维。从单容器迁移到分容器时，改的是 jobmanager.rpc.address 与容器数量，不改业务 SQL。

## 九、端口与网络

| 端口 | 用途 | 暴露范围 |
| --- | --- | --- |
| 8081 | Web UI 与 REST 提交接口 | 宿主与同网络容器 |
| 6123 | JM 与 TM 内部 RPC | 容器内部 |

同网络容器通过别名 flink 访问 REST 接口，地址是 http://flink:8081。宿主通过 http://localhost:8081 访问。两个地址指向同一个服务，使用场景不同。

> 容器内访问不能写 localhost:8081。那指向容器自己。写服务名 flink 才能解析到集群容器。
