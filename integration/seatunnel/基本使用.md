> **本文范围**：集群已装好之后怎么用。讲作业配置写法、三种提交方式、状态查看与连接器机制。本文只做独立集群的基本操作，不接 MySQL、不接 Doris。

# SeaTunnel 基本使用

> **一句话结论**：写一份 .conf 配置描述源与目标，用本地模式调试、用 REST API 提交。查状态看 system-monitoring-information 接口，看结果看 docker logs。

> **本文解决什么**：装完 SeaTunnel 后怎么写作业、怎么提交、怎么查结果、怎么加连接器。
>
> **适用谁**：已完成安装教程验收、想动手跑作业的用户。
>
> **读完能做什么**：从零写一份 FakeSource 作业，用两种方式跑通，查看集群状态，理解连接器加载机制。

---

## 一、入口总览

| 入口 | 怎么进 | 用来做什么 |
| --- | --- | --- |
| REST API | curl 调 18081 | 提交作业、查集群信息 |
| seatunnel.sh | docker exec 进容器 | 本地调试、集群提交、列作业 |
| docker logs | 容器日志 | 看作业输出与异常 |

> 所有入口都连到同一个容器。容器名 seatunnel。进入容器的固定写法是 docker exec seatunnel。脚本路径是 /opt/seatunnel/bin/seatunnel.sh。

## 二、作业配置文件

SeaTunnel 用 HOCON 格式描述作业，后缀 .conf。三段结构：env 定参数，source 定来源，sink 定去向。transform 可省略。

下面是一个带转换的完整示例。先把文件写到作业目录。

```bash
cat > /Users/wenhuadong/docker/integration/seatunnel/jobs/fake_to_console.conf <<'EOF'
env {
  parallelism = 1
  job.mode = "BATCH"
}

source {
  FakeSource {
    plugin_output = "fake"
    row.num = 10
    schema = {
      fields {
        id = "int"
        name = "string"
        age = "int"
      }
    }
  }
}

transform {
  FieldMapper {
    plugin_input = "fake"
    plugin_output = "mapped"
    field_mapper = {
      id = id
      name = name
      age = age
    }
  }
}

sink {
  Console {
    plugin_input = "mapped"
  }
}
EOF
```

| 段落 | 本示例作用 |
| --- | --- |
| env.parallelism | 作业并行度 |
| env.job.mode | BATCH 一次性跑完，STREAMING 持续运行 |
| source.FakeSource | 造 10 行模拟数据 |
| transform.FieldMapper | 字段映射，保持三列不变 |
| sink.Console | 打印到日志 |

数据流衔接靠 plugin_output 与 plugin_input。FakeSource 输出 fake，FieldMapper 消费 fake 再输出 mapped，Console 消费 mapped。

> 这两处字段是 3.x 的新写法。旧版是 result_table_name 与 source_table_name。写错会报配置解析失败。

### 2.1 关键参数

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| job.mode | BATCH / STREAMING | 批处理一次结束，流处理持续运行 |
| parallelism | 正整数 | 并行度，不能超过集群槽位 |
| checkpoint.interval | 毫秒数 | 流作业的检查点间隔 |

## 三、本地模式提交

本地模式在提交进程内启动作业，适合调试配置。作业随命令结束而结束。

```bash
docker exec seatunnel \
  /opt/seatunnel/bin/seatunnel.sh -m local \
  -c /jobs/fake_to_console.conf
```

预期输出：日志末尾打印 10 行模拟数据，最后显示作业正常结束。

| 参数 | 作用 |
| --- | --- |
| -m local | 本地模式，进程内执行 |
| -c | 指定作业配置文件路径 |

> 本地模式验证的是配置解析与连接器可用。它不经过集群调度。要验证集群提交链路，用下一节的 REST API。

## 四、REST API 提交

REST API 把作业交给常驻集群执行，是正式运行的推荐方式。作业描述用 JSON 提交。

先把作业写成 JSON 文件。

```bash
cat > /Users/wenhuadong/docker/integration/seatunnel/jobs/fake_to_console.json <<'EOF'
{
  "env": { "job.name": "fake-to-console", "job.mode": "BATCH" },
  "source": [
    {
      "plugin_name": "FakeSource",
      "plugin_output": "fake",
      "row.num": 10,
      "schema": { "fields": { "id": "int", "name": "string", "age": "int" } }
    }
  ],
  "transform": [],
  "sink": [
    { "plugin_name": "Console", "plugin_input": ["fake"] }
  ]
}
EOF
```

提交作业：

```bash
curl -fsS -X POST http://localhost:18081/submit-job \
  -H "Content-Type: application/json" \
  -d @/Users/wenhuadong/docker/integration/seatunnel/jobs/fake_to_console.json; echo
```

预期输出：返回 JSON，含作业号。随后 docker logs 出现 10 行模拟数据。

```bash
docker logs seatunnel --tail 60
```

| 字段 | 作用 |
| --- | --- |
| job.name | 作业显示名 |
| plugin_name | 连接器名，如 FakeSource |
| plugin_output / plugin_input | 数据流衔接，与 .conf 对应 |

> JSON 与 .conf 是同一份作业的两种写法。脚本提交用 .conf，REST 提交用 JSON。字段一一对应，只是 JSON 用数组与点号键。

## 五、集群模式提交

集群模式把作业提交给 Zeta 集群，提交者退出后作业继续运行。适合长跑流作业。

```bash
docker exec seatunnel \
  /opt/seatunnel/bin/seatunnel.sh -m cluster \
  -c /jobs/fake_to_console.conf
```

| 参数 | 作用 |
| --- | --- |
| -m cluster | 集群模式，提交到 Zeta 集群 |
| -c | 指定作业配置文件路径 |

> 集群模式的集群地址从 config/hazelcast-client.yaml 读取。单节点容器默认指向自身。REST API 提交是集群提交的等价方式，脚本化场景更常用。两者选一个即可。

## 六、查看状态与作业

```bash
# 集群节点信息
curl -fsS http://localhost:18081/system-monitoring-information; echo

# 列出运行中作业
docker exec seatunnel /opt/seatunnel/bin/seatunnel.sh -l
```

| 想做什么 | 命令或入口 |
| --- | --- |
| 看集群节点 | curl system-monitoring-information |
| 看作业列表 | seatunnel.sh -l |
| 看作业输出 | docker logs seatunnel |
| 看作业报错 | docker logs seatunnel 筛 exception |

> Console 输出写进 worker 的 stdout，落到 docker logs。排查作业失败先看 docker logs 里的异常堆栈。

## 七、连接器机制

连接器决定作业能读写哪些数据源。它以 jar 文件形式放在容器的 /opt/seatunnel/connectors/ 目录。

| 项 | 说明 |
| --- | --- |
| 默认内置 | FakeSource、Console |
| 存放位置 | /opt/seatunnel/connectors/ |
| 加载时机 | 集群启动时扫描目录 |

> 镜像默认只带 FakeSource 与 Console。对接 MySQL、Doris、Kafka 时，需要把对应 connector jar 放进 connectors/ 目录再重启容器。这是后续外部对接阶段的事，本阶段不涉及。

## 八、故障速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 配置解析报错 | 字段名写错或旧写法 | 检查 plugin_output / plugin_input |
| 报连接器未找到 | 镜像只带 fake 与 console | 换这两个连接器，或补 jar |
| 作业提交无反应 | REST API 未就绪 | 先 curl system-monitoring-information |
| Console 无输出 | 作业在集群执行 | 看 docker logs 而非提交命令输出 |
| -m cluster 连不上 | hazelcast-client 地址不对 | 单节点用 REST API 提交更省事 |
| 并行度超限 | parallelism 大于槽位 | 调小 parallelism |

## 九、小结

1. 作业是三段式配置：env、source、sink。transform 可省略。
2. 数据流用 plugin_output 与 plugin_input 衔接，不用旧字段名。
3. 本地模式调试配置，REST API 正式提交。两者目的不同。
4. Console 输出落到 docker logs，不在提交命令的返回里。
5. 连接器以 jar 形式放 connectors/ 目录，默认只有 fake 与 console。
