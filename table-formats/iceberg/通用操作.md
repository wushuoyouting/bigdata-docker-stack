# Iceberg 通用操作

> **一句话结论**：Iceberg 用法是「加 jar、建 catalog、建表、读写」。对象存储统一用 MinIO。本机学习选 hadoop 类型 catalog，warehouse 指向 s3://lakehouse/iceberg/。

> **本文解决什么**：给出从零建表到读写、时间旅行、维护的完整命令。

> **适用谁**：已装好 MinIO，用 Spark 操作 Iceberg 的人。

> **读完能做什么**：独立建 catalog、建表、批量写、时间旅行、清理快照，并排查常见错误。

> **与基本使用.md 的分工**：本册走 MinIO 与 hadoop catalog。本机 Quickstart 的 REST Catalog 与 Flink SQL 操作见 基本使用.md。

## 二、依赖 jar

### 2.1 Spark 方式

下 iceberg-spark-runtime jar，放进 Spark 的 jars 目录。

```
iceberg-spark-runtime-3.5_2.12-<ICEBERG_VERSION>.jar
```

启动 spark-sql 时带三个配置。

```
spark-sql \
  --packages org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:<ICEBERG_VERSION> \
  --conf spark.sql.extensions=org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions \
  --conf spark.sql.catalog.iceberg_lake=org.apache.iceberg.spark.SparkCatalog \
  --conf spark.sql.catalog.iceberg_lake.type=hadoop \
  --conf spark.sql.catalog.iceberg_lake.warehouse=s3://lakehouse/iceberg/
```

### 2.2 S3 支持

hadoop 类型 catalog 走 Hadoop FileSystem。需让 s3a 识别 MinIO。

```
spark.hadoop.fs.s3a.endpoint=http://minio:9000
spark.hadoop.fs.s3a.access.key=<MINIO_AK>
spark.hadoop.fs.s3a.secret.key=<MINIO_SK>
spark.hadoop.fs.s3a.path.style.access=true
spark.hadoop.fs.s3a.impl=org.apache.hadoop.fs.s3a.S3AFileSystem
```

注意：endpoint 写容器内地址 http://minio:9000。写 localhost 在容器里指向自己。

## 三、建库建表

### 3.1 切换 catalog

```
USE iceberg_lake;
CREATE DATABASE IF NOT EXISTS demo_db;
USE demo_db;
```

### 3.2 建表

```
CREATE TABLE IF NOT EXISTS demo_db.events (
  id BIGINT,
  user_id BIGINT,
  event_name STRING,
  event_time TIMESTAMP,
  dt STRING
)
USING iceberg
PARTITIONED BY (dt)
TBLPROPERTIES (
  'format-version' = '2',
  'write.format.default' = 'parquet'
);
```

预期：SHOW TABLES 返回 events。

说明：format-version 2 支持行级删除与 MOR。version 1 只支持追加。

## 四、写入数据

### 4.1 批量追加

```
INSERT INTO demo_db.events VALUES
  (1, 1001, 'login',   TIMESTAMP'2026-11-17 09:00:00', '2026-11-17'),
  (2, 1002, 'purchase',TIMESTAMP'2026-11-17 10:30:00', '2026-11-17');
```

预期：SELECT count(*) 返回 2。

### 4.2 行级更新

version 2 表支持 UPDATE 与 MERGE INTO。

```
UPDATE demo_db.events
SET event_name = 'logout'
WHERE id = 1;
```

### 4.3 MERGE upsert

```
MERGE INTO demo_db.events AS t
USING (SELECT 2 AS id, 'refund' AS event_name) AS s
ON t.id = s.id
WHEN MATCHED THEN UPDATE SET t.event_name = s.event_name
WHEN NOT MATCHED THEN INSERT (id, event_name) VALUES (s.id, s.event_name);
```

预期：id 为 2 的行 event_name 变成 refund。

## 五、查询与时间旅行

### 5.1 普通查询

```
SELECT * FROM demo_db.events WHERE dt = '2026-11-17';
```

### 5.2 查快照历史

```
SELECT snapshot_id, committed_at, operation
FROM demo_db.events.snapshots;
```

预期：每次 INSERT、UPDATE、MERGE 各占一行。

### 5.3 按快照号读

```
SELECT * FROM demo_db.events VERSION AS OF 1234567890;
```

### 5.4 按时间戳读

```
SELECT * FROM demo_db.events TIMESTAMP AS OF '2026-11-17 09:00:00';
```

### 5.5 回滚

```
CALL iceberg_lake.system.rollback_to_snapshot('demo_db.events', 1234567890);
```

注意：回滚改的是当前指针，不删除已有数据。

## 六、schema 与分区演进

### 6.1 加列

```
ALTER TABLE demo_db.events ADD COLUMNS (channel STRING);
```

预期：旧行的 channel 读成 null。

### 6.2 改分区

```
CALL iceberg_lake.system.add_partition_field(
  table => 'demo_db.events',
  field => 'user_id',
  transform => 'bucket(16)'
);
```

注意：新分区只影响后续写入，旧数据布局不变。

---

## 七、快照维护

### 7.1 过期快照

```
CALL iceberg_lake.system.expire_snapshots(
  table => 'demo_db.events',
  older_than => TIMESTAMP'2026-10-01 00:00:00',
  retain_last => 5
);
```

预期：旧快照与其专属数据文件被清理。

### 7.2 合并小文件

```
CALL iceberg_lake.system.rewrite_data_files(table => 'demo_db.events');
```

### 7.3 清理孤儿文件

```
CALL iceberg_lake.system.remove_orphan_files(table => 'demo_db.events');
```

注意：先跑 expire_snapshots，再跑 remove_orphan_files。顺序反了会漏清。

## 八、使用案例

### 8.1 场景背景

业务库的订单表持续更新。要求分钟级同步到湖上，供 Trino 与 Spark 共读。

### 8.2 数据流

```
MySQL binlog
  └─ Flink CDC 捕获变更
       └─ Iceberg 表 demo_db.orders（version 2，MOR）
            ├─ Spark 离线报表
            └─ Trino 交互查询
```

### 8.3 落地步骤

① 建 version 2 表，开启 MOR。

```
CREATE TABLE demo_db.orders (
  order_id BIGINT,
  status STRING,
  amount DECIMAL(18,2),
  updated_at TIMESTAMP,
  PRIMARY KEY (order_id) NOT ENFORCED
)
USING iceberg
TBLPROPERTIES (
  'format-version' = '2',
  'write.update.mode' = 'merge-on-read',
  'write.delete.mode' = 'merge-on-read',
  'write.merge.mode' = 'merge-on-read'
);
```

② 用 Flink CDC 作业持续写入，checkpoint 间隔设 10 秒。

③ 用 Spark 验证最新状态。

```
SELECT status, count(*) FROM demo_db.orders GROUP BY status;
```

④ 在 MinIO 上确认 meta 与 data 目录都产出文件。

```
docker run --rm --network whd-net --entrypoint /bin/sh minio/mc:<MC_TAG> -c '
  mc alias set lake http://minio:9000 "<MINIO_AK>" "<MINIO_SK>" &&
  mc ls --recursive lake/lakehouse/iceberg/demo_db/orders/ | head -30
'
```

### 8.4 验证判据

| 项 | 判据 |
| --- | --- |
| 写入 | SELECT count(*) 与源表一致 |
| 更新 | 改源表一行，湖上值同步变化 |
| 快照 | events.snapshots 行数随提交增加 |
| 落盘 | MinIO 上有 metadata 与 data 两类文件 |

### 8.5 踩坑表

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| No FileSystem for scheme s3a | 缺 s3a jar | 补 hadoop-aws 与 aws-java-sdk-bundle |
| The bucket does not exist | endpoint 写成 localhost | 改 http://minio:9000 |
| SignatureDoesNotMatch | 未开 path-style | 设 fs.s3a.path.style.access=true |
| UPDATE 报不支持 | format-version 是 1 | 建表时设 2 |
| 查询越来越慢 | delete 文件堆积 | 跑 rewrite_data_files |
| 元数据文件暴涨 | 小批量高频提交 | 改为微批写入，拉长提交间隔 |

## 九、本篇小结

① Iceberg 用法是加 jar、建 catalog、建表、读写四步。

② 本机通用方案用 hadoop catalog，warehouse 指向 s3://lakehouse/iceberg/。

③ 行级更新要 format-version 2，upsert 用 MERGE INTO。

④ 时间旅行靠快照，回滚只改指针不删数据。

⑤ 定期跑 expire_snapshots 与 rewrite_data_files，控制元数据与小文件。
