# Hudi 原理

> **一句话结论**：Hudi 用「Timeline 加文件组加索引」支撑行级更新。每次提交在 Timeline 上记一个 instant。索引决定更新落到哪个文件组。COW 重写整文件，MOR 写增量日志。

> **本文解决什么**：讲清 Hudi 的 Timeline、文件组、索引、COW 与 MOR 的工作方式。
>
> **适用谁**：已选定 Hudi，做 CDC 入湖或近实时更新的人。
>
> **读完能做什么**：判断该选 COW 还是 MOR，理解索引为何决定性能，解释增量查询的原理。

---

## 一、整体架构

Hudi 分三层。上层是引擎，中层是 Hudi 表服务，下层是对象存储。

```
引擎：Spark / Flink / Trino / Hive
        ↓ 写记录、读快照或增量
表服务：Timeline + 索引 + 文件组 + 后台清理
        ↓ S3 API
对象存储：MinIO 的 s3://lakehouse/hudi/
```

Hudi 本体是 jar。它挂进引擎才工作。Hudi 不是服务，没有独立进程。

### 1.1 元数据模型决定更新机制

四种开放表格式都是 jar。差异不在是否独立部署，在元数据模型与写路径。

Hudi 的元数据模型是 Timeline 加文件组加索引。索引把记录键映射到文件组，所以更新能定位到具体文件。COW 重写整个基础文件，MOR 把更新写进日志文件。这两种模式都由文件组结构决定，与 Catalog 存放位置无关。

Catalog 只负责表名到当前元数据的入口映射。Hudi 常用 hms 或 filesystem。换 Catalog 不改变 Timeline 结构，也不改变 COW 与 MOR 的行为。

一句话记住因果：写路径决定更新机制，元数据模型承载它，Catalog 只找入口。

## 二、核心概念

### 2.1 Timeline

Timeline 是 Hudi 的事务日志。每次操作追加一个 instant。

instant 记录动作类型、时间、状态。常见动作如下。

| 动作 | 含义 |
| --- | --- |
| commit | 一批写入完成 |
| deltacommit | MOR 的增量写入完成 |
| compaction | 日志合并进基础文件 |
| clean | 清理旧版本文件 |
| rollback | 回滚失败提交 |
| clustering | 重排文件布局 |

instant 有三种状态：requested、inflight、completed。只有 completed 对读者可见。

### 2.2 文件组

文件组是 Hudi 的存储单元。它由唯一的文件组 ID 标识。

一个文件组包含两部分。

① 基础文件。Parquet 列存，是不可变的历史版本。

② 日志文件。只存在于 MOR，记录增量更新。

同一条记录永远落到同一个文件组。这是索引要保证的事。

### 2.3 文件切片

一个基础文件加它后续的日志文件，构成一个文件切片。

每次提交生成新切片。旧切片保留支撑时间旅行与增量查询。

### 2.4 记录键

Hudi 用「记录键加分区路径」唯一标识一条记录。

记录键由用户指定。选错键会导致更新散落到多个文件组，性能骤降。

---

## 三、索引机制

索引把记录键映射到文件组 ID。它是 Hudi 更新性能的关键。

### 3.1 为什么需要索引

更新一条记录时，Hudi 要知道它原来在哪个文件组。

没有索引就得全表扫描。有索引则直接定位，避免读无关文件。

### 3.2 常用索引类型

| 索引 | 原理 | 特点 |
| --- | --- | --- |
| Bloom | 布隆过滤器判断键是否可能在某文件 | 默认，省空间，有误判 |
| Simple | 在内存中维护键到文件组的映射 | 快，内存占用高 |
| Bucket | 对键做哈希分桶 | 无需查找，扩展性好 |
| HBase | 外部 HBase 存映射 | 适合超大规模，需额外组件 |

### 3.3 索引选择

数据量中等用 Bloom。

键分布均匀、追求稳定性能用 Bucket。

已有 HBase 集群且键规模极大，用 HBase 索引。

---

## 四、写模式

### 4.1 COW

COW 是写时复制。更新一行时重写整个基础文件，生成新版本文件切片。

优点：读路径只有基础文件，查询快。

缺点：写放大明显，更新集中的表写入慢。

### 4.2 MOR

MOR 是读时合并。更新写进日志文件，不立即改基础文件。

读取时把基础文件与日志合并，得到最新值。

优点：写入快，适合高频小批量更新。

缺点：读时要合并，需后台 compaction 控制日志长度。

### 4.3 两种模式对比

| 项 | COW | MOR |
| --- | --- | --- |
| 写入延迟 | 高 | 低 |
| 查询延迟 | 低 | 中 |
| 写放大 | 大 | 小 |
| 后台维护 | clean 为主 | compaction 加 clean |
| 适合 | 读多写少 | 近实时写入 |

## 五、提交与并发

Hudi 用 Timeline 上的 instant 实现并发控制。

① 写者申请一个 instant，状态置为 requested。

② 写者写文件，状态改为 inflight。

③ 文件写完，状态改为 completed。

④ 读者只看 completed 的 instant。

两个写者同时提交时，Hudi 检测冲突并让一方重试。

---

## 六、四种查询

Hudi 提供四种读视图，区别在读哪个时间点的文件切片。

| 视图 | 读什么 | 用途 |
| --- | --- | --- |
| Snapshot | 最新已完成提交 | 看当前状态 |
| Incremental | 两次提交之间的变更 | 增量 ETL |
| Read Optimized | 只读基础文件 | 最快查询，可能不是最新 |
| Time Travel | 指定时间点的切片 | 回溯历史 |

### 6.1 增量查询原理

客户端给出一个 instant 时间。Hudi 返回该时间之后的变更记录。

变更来自新写的基础文件或日志文件。增量 ETL 据此只处理变化部分。

---

## 七、后台表服务

Hudi 把维护动作做成表服务，可同步或异步执行。

| 服务 | 作用 |
| --- | --- |
| Compaction | 合并日志文件进基础文件，仅 MOR |
| Clean | 删除不再被引用的旧文件切片 |
| Clustering | 重排文件，改善数据局部性 |
| Rollback | 清理失败提交留下的文件 |

不同步执行时，日志文件会越积越长，查询持续变慢。

---

## 八、代价与边界

① 记录键必须稳定且分布均匀。键倾斜会造成个别文件组过大。

② MOR 的读放大依赖 compaction 及时跟进。

③ 索引需要维护成本，超大规模要选外部索引。

④ Timeline 元数据会累积，需要定期 clean 与 archive。

---

## 九、本篇小结

① Hudi 的三根支柱是 Timeline、文件组、索引。

② instant 只有到 completed 才对读者可见。

③ 索引把记录键映射到文件组，决定更新性能。

④ COW 写慢读快，MOR 写快读慢，需后台 compaction。

⑤ 增量查询让下游只处理变化部分，是 Hudi 的核心价值。
