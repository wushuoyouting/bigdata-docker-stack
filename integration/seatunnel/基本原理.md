# SeaTunnel 基本原理

> **一句话结论**：SeaTunnel 是数据集成工具，用一份配置描述数据的来源与去向。它自带 Zeta 引擎默认运行，也可以把作业提交给 Flink 或 Spark。本机选 Zeta 独立运行，不交给 Flink。

> **本文解决什么**：理解 SeaTunnel 为何自带引擎、它和 Flink 到底是什么关系、一份作业如何从配置变成数据搬运。
>
> **适用谁**：准备安装 SeaTunnel，或想知道它和 Flink 取舍依据的用户。
>
> **读完能做什么**：判断该不该为 SeaTunnel 单独起容器，解释 Zeta 与 Flink 引擎的差异，读懂作业配置的三段结构。

---

## 一、SeaTunnel 是什么

SeaTunnel 是分布式数据集成工具。它做的是数据搬运：从一个数据源读出，写到另一个数据源。中间可以做字段映射、过滤等轻量转换。

它的典型用途有三类：整库迁移、多表同步、变更数据捕获（CDC）。它与计算引擎不同，它不做复杂业务计算，专注把数据从 A 搬到 B。

| 对比项 | SeaTunnel | Flink |
| --- | --- | --- |
| 定位 | 数据集成与同步 | 通用流批计算 |
| 核心动作 | 读源、写目标 | 任意计算逻辑 |
| 作业写法 | 一份配置描述源与目标 | SQL 或 Java 代码 |
| 自带引擎 | 有，Zeta | 本身就是引擎 |

> SeaTunnel 的架构理念是配置与引擎解耦。同一份作业配置，可以跑在 Zeta 上，也可以跑在 Flink 或 Spark 上。换引擎不换作业写法。

## 二、三种执行引擎

SeaTunnel 支持三种执行引擎。作业配置不变，换引擎只改启动命令。

| 引擎 | 英文名 | 定位 | 是否需独立部署 |
| --- | --- | --- | --- |
| Zeta | SeaTunnel Engine | 数据同步专用，自研 | 是 |
| Flink | Apache Flink | 通用流处理 | 否，复用已有集群 |
| Spark | Apache Spark | 通用批处理 | 否，复用已有集群 |

**Zeta 引擎**是官方主推的默认引擎。它专为数据同步场景优化，无外部依赖，资源消耗低，启动快，对 CDC 与多表同步支持最完整。它还自带 REST API 供作业提交与监控。

**Flink 引擎**把作业提交到已有 Flink 集群执行。适合已经稳定运行 Flink、想复用现有体系的团队。

**Spark 引擎**以批处理为主，不支持 CDC 与 schema 演变。适合已有 Spark 体系、任务以离线为主的团队。

| 维度 | Zeta | Flink | Spark |
| --- | --- | --- | --- |
| 外部依赖 | 无 | 可选 ZooKeeper | YARN 或 Mesos |
| 资源消耗 | 低 | 中 | 高 |
| 启动速度 | 快 | 中 | 慢 |
| CDC 支持 | 有 | 有 | 无 |
| 自带 REST API | 有 | 无 | 无 |

> 官方初选规则：没有现成 Flink 或 Spark 运维体系，优先从 Zeta 开始。已有 Flink 集群且想复用，才选 Flink。

## 三、为什么"交给 Flink"是旧认知

SeaTunnel 的历史分三个阶段。

① 早期叫 Waterdrop，是运行在 Spark 上的一个工具，自己没有引擎。

② 后来改名 SeaTunnel，同时支持 Spark 与 Flink 两套引擎。作业仍依赖外部计算引擎执行。

③ 从 2.3.x 起引入自研的 Zeta 引擎。Zeta 逐步成为默认推荐，作业不再必须依赖 Flink 或 Spark。

所以"SeaTunnel 交给 Flink 执行"描述的是第二阶段的状态。现在的 SeaTunnel 自带 Zeta 引擎，独立部署即可运行。Flink 引擎保留下来，只服务那些已有 Flink 集群、想复用的团队。

> 3.0 起还引入 Edge Agent，用于边缘节点数据采集。它进一步说明 SeaTunnel 是一个自带运行体系的集成平台，不是 Flink 的附属工具。

## 四、Zeta 引擎架构

Zeta 引擎分两类角色，与 Flink 的 JobManager 与 TaskManager 对应关系类似。

| 角色 | 职责 | 是否常驻 |
| --- | --- | --- |
| Master | 调度作业、协调成员、维护集群元数据 | 是 |
| Worker | 执行数据读写、上报状态 | 是 |

Master 是集群的协调者。它接收作业，把任务分配给 Worker，维护成员列表与作业状态。REST API 也跑在 Master 上，容器内端口 8080，宿主映射 18081。

Worker 是执行者。它运行数据搬运的读写算子，处理实际的数据流。一个集群可有多个 Worker。

> Zeta 用 Hazelcast 做集群成员通信，端口 5801。这与 Flink 用 6123 做 RPC 是同一个道理。5801 只在成员之间用，不对外暴露。

### 4.1 单节点 master_and_worker

镜像脚本 seatunnel-cluster.sh 支持三种角色：master、worker、master_and_worker。不带参数默认是第三种。

master_and_worker 表示一个进程同时承担调度与执行。单容器因此就是一个完整的单节点集群。本机采用这个角色，省掉多容器。

## 五、作业模型

SeaTunnel 用一份配置文件描述作业。配置是 HOCON 格式，后缀 .conf。它由三段组成。

| 段落 | 作用 | 是否必填 |
| --- | --- | --- |
| env | 作业级参数，如并行度、运行模式 | 是 |
| source | 数据从哪里读 | 是 |
| transform | 中间转换，可省略 | 否 |
| sink | 数据写到哪里 | 是 |

三段之外，source 与 sink 用 plugin_output 与 plugin_input 两个字段把数据流串起来。

| 字段 | 写在哪 | 作用 |
| --- | --- | --- |
| plugin_output | source、transform | 给本段产出的数据流命名 |
| plugin_input | transform、sink | 声明本段消费哪条数据流 |

> 这两个字段是 3.x 的新写法。旧版用 result_table_name 与 source_table_name。升级到 3.x 时要替换，否则作业解析报错。

### 5.1 一个最小作业

下面是最小可跑的作业：FakeSource 造 10 行数据，Console 打印到控制台。

```hocon
env {
  parallelism = 1
  job.mode = "BATCH"
}

source {
  FakeSource {
    plugin_output = "fake"
    row.num = 10
    schema = {
      fields {
        name = "string"
        age = "int"
      }
    }
  }
}

sink {
  Console {
    plugin_input = "fake"
  }
}
```

FakeSource 输出一条名为 fake 的数据流。Console 声明消费 fake。数据从 source 流向 sink，无需 transform。

## 六、作业提交的三种方式

作业配置写好之后，有三种方式让它跑起来。

| 方式 | 命令或入口 | 特点 | 适用 |
| --- | --- | --- | --- |
| 本地模式 | seatunnel.sh -m local | 在提交进程内启动作业 | 调试、验证配置 |
| 集群模式 | seatunnel.sh -m cluster | 提交到 Zeta 集群 | 生产、正式运行 |
| REST API | curl 调 18081 | 脚本化提交与监控 | 自动化、外部系统接入 |

本地模式与集群模式的本质区别在于作业在哪里执行。本地模式在提交者进程内执行，进程结束作业结束。集群模式把作业交给常驻的 Zeta 集群，提交者退出后作业继续运行。

> 本机验收用本地模式跑冒烟，确认配置解析与连接器可用。正式跑同步用 REST API 或集群模式，交给常驻容器执行。

## 七、本机选型依据

本机已有一套 Flink 单容器集群，限 1G 内存、2 个槽位。它主业是写湖链路，从 Doris 读 ADS 结果写 Paimon。

SeaTunnel 不交给这套 Flink，理由有三。

① 内存。Flink 单容器限 1G，再加同步作业会挤占写湖作业的资源。

② 职责。写湖是计算任务，数据同步是搬运任务。两者混在一个引擎里，故障互相牵连。

③ 官方取向。SeaTunnel 3.x 默认主推 Zeta，同步场景下 Zeta 更轻、CDC 支持更好、自带 REST API。

因此本机为 SeaTunnel 单独起一个 Zeta 单容器。它独立于 Flink，两者通过 Doris、MinIO 等数据端点间接协作，不共享进程。

> 备选方案是走 Flink 引擎，让 SeaTunnel 只做配置层、执行交给 Flink。本机内存紧张，不选。若将来换成内存充足的生产集群，可以再评估复用 Flink。
