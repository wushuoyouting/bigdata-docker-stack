# SeaTunnel 安装教程

> **一句话结论**：一个 apache/seatunnel:3.1.0 容器，用镜像自带的 seatunnel-cluster.sh 起单节点 master_and_worker。宿主前端端口映射 18081，容器内 HTTP 端口 8080。验收两条：REST API 能查集群信息，FakeSource 作业能跑通并打印数据。

> **本文解决什么**：本机需要一套能独立运行的数据集成引擎。本文给出单容器安装法，无需分 master 与 worker 起多个容器。
>
> **适用谁**：已装 Docker Desktop、懂基本 docker 命令、想在本机跑 SeaTunnel 的用户。
>
> **读完能做什么**：一条 docker run 起完整集群、验证安装、停止与重来、处理常见启动故障。

> **核对时点**：2026-11-22。macOS arm64 / Docker Desktop。whd-net 已含 MinIO、Doris、Flink、Superset 等组件，固定 IP 已排到 .18。SeaTunnel 取 .19。前端端口取 18081，18080 已被占用，需先查宿主占用。
>
> **本机实测**：apache/seatunnel:3.1.0 提供 linux/arm64 原生镜像。安装命令与作业模板来自官方 Docker 文档，待本机落地后回填实测输出。

## 一、验收对照

| # | 判据 | 验证命令 |
| --- | --- | --- |
| ① | 容器状态 Up | docker ps --filter name=seatunnel |
| ② | REST API 返回集群信息 | curl -fsS http://localhost:18081/system-monitoring-information |
| ③ | 本地模式作业跑通 | docker exec seatunnel seatunnel.sh -m local 跑模板 |
| ④ | REST 提交作业返回作业号 | curl -X POST 18081/submit-job |

**基线参数**：容器名 seatunnel，别名 seatunnel，固定 IP 172.30.0.19，加入 whd-net。宿主映射 18081，容器内 HTTP 端口 8080。5801 是内部通信端口，不映射宿主。

## 二、安装前复核

```bash
lsof -nP -iTCP:18081 -sTCP:LISTEN || echo '18081 空闲'

docker ps -a --filter name=seatunnel \
  --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'

docker network inspect whd-net \
  --format '{{range .Containers}}{{.Name}} | {{.IPv4Address}}{{println}}{{end}}'

docker image inspect apache/seatunnel:3.1.0 \
  --format '{{.Os}}/{{.Architecture}}' 2>/dev/null || echo '镜像未拉取'

mkdir -p /Users/wenhuadong/docker/integration/seatunnel/jobs && echo 'jobs 目录就绪'
```

| 检查项 | 期望 | 不满足时 |
| --- | --- | --- |
| 18081 | 空闲 | 停掉占用进程后复查 |
| 旧容器 | 无同名 seatunnel | docker rm -f seatunnel |
| whd-net | 存在，172.30.0.19 未被占用 | 占用时换一个 .19 以后的地址 |
| 镜像架构 | linux/arm64 | amd64 时加 --platform linux/amd64 |
| jobs/ | 目录存在 | mkdir -p 创建 |

> **注意**：镜像约 3.6G，首次拉取较慢。18081 是本仓库未占用端口，18080 已被占用故取 18081。宿主可能有其他本地服务监听，先查 lsof 再启动。

## 三、启动集群

### 3.1 为什么这样启动

SeaTunnel 官方镜像没有定义 ENTRYPOINT 与 CMD。容器启动后什么都不做，必须显式传入命令。

镜像自带集群脚本 seatunnel-cluster.sh。该脚本不带参数时默认以 master_and_worker 角色启动节点。一个进程同时承担调度与执行，单容器因此就是单节点集群。所以把该脚本作为容器命令传入即可。

### 3.2 一条命令启动

```bash
docker run -d \
  --name seatunnel \
  --network whd-net \
  --network-alias seatunnel \
  --ip 172.30.0.19 \
  -p 18081:8080 \
  -v /Users/wenhuadong/docker/integration/seatunnel/jobs:/jobs \
  apache/seatunnel:3.1.0 \
  /opt/seatunnel/bin/seatunnel-cluster.sh
```

预期输出：docker run 返回一串容器 ID。docker ps 显示容器 Up。

| 参数 | 作用 |
| --- | --- |
| 容器名与别名 seatunnel | 同网络其他组件按此名访问 REST 接口 |
| --ip 172.30.0.19 | 固定 IP，重建不漂移 |
| -p 18081:8080 | 宿主 18081 映射容器 8080，暴露 Web UI 与 REST API |
| -v jobs:/jobs | 把作业配置挂进容器 |
| seatunnel-cluster.sh | 以 master_and_worker 角色启动集群 |

> 容器内 HTTP 端口仍是 8080，宿主用 18081 访问。同网络的其他容器访问本服务时，写 http://seatunnel:8080，走容器内端口。

> 单节点 master_and_worker 的 5801 只在容器内部使用。不映射宿主。将来扩多节点集群时，成员在 whd-net 内直接用 5801 互通，同样不需要映射宿主。

### 3.3 等待就绪

```bash
for i in $(seq 1 40); do
  curl -fsS http://localhost:18081/system-monitoring-information \
    -o /dev/null 2>/dev/null && {
      echo 'REST API 就绪'; break
    }
  echo "第 ${i} 次：未就绪，等 3s"; sleep 3
done
```

预期输出：最后一行显示 REST API 就绪。SeaTunnel 从启动到 REST API 可用通常需十几秒。

## 四、逐条验收

```bash
# ① 容器状态
docker ps --filter name=seatunnel --format '{{.Names}}\t{{.Status}}\t{{.Ports}}'

# ② REST API 集群信息
curl -fsS http://localhost:18081/system-monitoring-information; echo

# ③ 本地模式冒烟，跑官方模板 FakeSource → Console
docker exec seatunnel \
  /opt/seatunnel/bin/seatunnel.sh -m local \
  -c config/v2.batch.config.template

# ④ REST API 提交作业
curl -fsS -X POST http://localhost:18081/submit-job \
  -H "Content-Type: application/json" \
  -d '{
    "env": { "job.name": "smoke", "job.mode": "BATCH" },
    "source": [{
      "plugin_name": "FakeSource",
      "plugin_output": "fake",
      "row.num": 5,
      "schema": { "fields": { "id": "int", "name": "string" } }
    }],
    "transform": [],
    "sink": [{ "plugin_name": "Console", "plugin_input": ["fake"] }]
  }'; echo
```

| # | 通过标准 |
| --- | --- |
| ① | 状态 Up，端口显示 0.0.0.0:18081-&gt;8080/tcp |
| ② | 返回 HTTP 200 与 JSON，含集群节点信息 |
| ③ | 日志末尾打印多行模拟数据，作业正常结束 |
| ④ | 返回 JSON 含作业号，docker logs seatunnel 出现模拟数据行 |

> 第 ③ 步的本地模式在容器进程内启动作业，用于验证配置解析与连接器可用。它不占用集群槽位。第 ④ 步的 REST API 提交才是把作业交给常驻集群执行，Console 输出会出现在 docker logs 里。

## 五、停止与重来

```bash
# 停与起
docker stop seatunnel
docker start seatunnel

# 看日志
docker logs -f seatunnel --tail 100

# 完全重来，保留作业目录
docker rm -f seatunnel
# 重跑第 3.2 节的 docker run
```

| 动作 | 数据安全 |
| --- | --- |
| stop / start | 容器可写层与作业目录全保留 |
| docker rm -f | jobs 是绑定挂载，保留 |
| docker rm -v | 禁止，会删命名卷 |
| rm -rf jobs/* | 只有明确重置作业才做 |

> 起停顺序只有容器一个。SeaTunnel 单节点没有先 master 后 worker 的要求。独立安装阶段没有长跑作业，重来无数据风险。

## 六、故障速查

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 端口被占 | 宿主其他服务监听 18081 | lsof 找到进程并处理 |
| 容器起后立刻退出 | 脚本或配置报错 | docker logs seatunnel 看首行错误 |
| REST API 一直未就绪 | 启动慢或端口未通 | 等满 40 次循环再看日志 |
| 本地模式报连接器缺失 | 镜像只带 FakeSource 与 Console | 换这两个连接器，或按基本使用装 jar |
| 作业解析报错 | 用了旧字段名 | 检查是否误写 result_table_name |
| 宿主访问不了 18081 | 容器未起或端口不通 | docker ps 与 curl 复查 |
| 容器名冲突 | 同名容器已存在 | 先 docker rm -f seatunnel |

## 七、小结

1. 独立安装只起一个容器。master 与 worker 由 seatunnel-cluster.sh 在同一容器内启动。
2. 镜像没有 ENTRYPOINT，命令必须显式传入。不带参数默认 master_and_worker。
3. 宿主映射 18081，容器内 HTTP 端口 8080。5801 内部通信端口不暴露，跨容器访问用别名 seatunnel。
4. 验收两条：REST API 返回集群信息；FakeSource 作业能跑通并打印数据。
5. MySQL、Doris、Kafka 的对接不在本次范围。需要时读基本使用里的连接器安装。
