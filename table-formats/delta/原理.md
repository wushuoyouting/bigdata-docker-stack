# Delta Lake 原理

> **一句话结论**：Delta Lake 用「事务日志加 checkpoint」实现 ACID。每次写操作在 _delta_log 追加一条 JSON 记录。读方按顺序重放日志得到表的当前状态。删除向量让行级更新不必重写整份 Parquet。

> **本文解决什么**：讲清 Delta Lake 的事务日志、checkpoint、并发控制与删除向量。
>
> **适用谁**：已选定 Delta Lake，重度使用 Spark 的人。
>
> **读完能做什么**：解释一次写入产生了哪些日志，理解冲突检测与时间旅行，判断何时触发 checkpoint。

---

## 一、整体架构

Delta Lake 分三层。上层是 Spark，中层是事务日志，下层是对象存储。

```
引擎：Spark / Flink / Trino / Presto
        ↓ DataFrame API 与 SQL
事务日志：_delta_log 目录下的 JSON 与 checkpoint
        ↓ S3 API
对象存储：MinIO 的 s3://lakehouse/delta/
```

Delta Lake 与 Spark 结合最紧。其它引擎通过各自 connector 读取。

---

## 二、目录结构

一张 Delta 表在 MinIO 上是一个目录。

```
s3://lakehouse/delta/demo_db/events/
├── _delta_log/
│   ├── 00000000000000000000.json
│   ├── 00000000000000000001.json
│   ├── 00000000000000000002.json
│   ├── 00000000000000000002.checkpoint.parquet
│   └── _last_checkpoint
├── part-00000-xxx.parquet
├── part-00001-yyy.parquet
└── deletion_vector/
    └── 00000-1-zz.deletion_vector.bin
```

关键目录说明。

| 目录 | 内容 |
| --- | --- |
| _delta_log | 事务日志，JSON 逐版本记录，checkpoint 定期汇总 |
| 根目录 | 数据文件，默认 Parquet |
| deletion_vector | 删除向量，标记被删行 |

## 三、事务日志

### 3.1 日志内容

每次写操作生成一个 JSON 文件，文件名是 20 位版本号。

文件里记录三类动作。

| 动作 | 含义 |
| --- | --- |
| add | 新增一个数据文件 |
| remove | 标记一个数据文件失效 |
| metaData | schema、分区、格式等元数据 |

一次 INSERT 产生若干 add。一次 UPDATE 产生 add 加 remove。

### 3.2 版本重放

读表时，引擎从版本 0 开始顺序重放所有 JSON。

重放的产物是当前有效的数据文件列表。这就是表的当前快照。

### 3.3 checkpoint

版本多了以后重放变慢。Delta 每 10 个版本写一个 checkpoint。

checkpoint 把此前所有日志汇总成一个 Parquet 文件。

读表时先找最近的 checkpoint，再重放它之后的 JSON。

_last_checkpoint 记录最新 checkpoint 的位置，避免扫描目录。

## 四、ACID 实现

### 4.1 原子性

写者先写数据文件，再写日志 JSON。

日志 JSON 用「写临时文件加原子重命名」落盘。只有重命名成功，本次提交才可见。

读者只看已完成的日志版本，看不到半途文件。

### 4.2 隔离性

读者启动时锁定一个版本号。之后的新日志不影响这次读取。

这叫快照隔离。

### 4.3 并发控制

Delta 用乐观并发控制。

① 写者读取当前版本 N。

② 写者写数据文件与版本 N+1 的日志。

③ 提交前检查版本 N+1 是否已被占用。

④ 若被占用，检测冲突。无冲突则重试，有冲突则中止。

### 4.4 冲突判定

两笔交易冲突的条件：

- 改了同一分区的数据
- 改了表的 schema 或分区规则
- 同时做了不兼容的元数据变更

只读互不冲突。写不同分区通常也不冲突。

## 五、删除向量

### 5.1 行级删除的难题

Parquet 是不可变的。删一行传统上要重写整份文件。

删除量大时，重写成本很高。

### 5.2 删除向量做法

删除向量是一个位图。它标记某个数据文件里哪些行被删。

引擎读数据时跳过被标记的行，不必重写 Parquet。

### 5.3 启用条件

删除向量默认关闭。建表时开两个属性。

```
delta.enableDeletionVectors = true
delta.feature.deletionVectors = supported
```

### 5.4 代价

删除向量越多，读时要处理的位图越多。

后台要定期做 OPTIMIZE，把删除真正落到数据文件。

---

## 六、关键能力如何落地

### 6.1 时间旅行

按版本号或时间戳读历史日志，重放到指定版本即可。

历史数据文件未删除时，任意版本都能读。

### 6.2 schema 演进

加列只改 metaData 动作，不碰数据文件。

旧文件缺的列读成 null。改类型时做兼容性校验。

### 6.3 流式读写

Structured Streaming 把 Delta 表当源或汇。

每次微批追加一个日志版本。流读按版本顺序消费，天然 exactly-once。

---

## 七、后台维护

| 动作 | 作用 |
| --- | --- |
| OPTIMIZE | 合并小文件，应用删除向量 |
| VACUUM | 删除不再被引用的旧数据文件 |
| checkpoint | 汇总日志，加速重放 |

VACUUM 有保留期，默认 7 天。保留期内的数据仍可时间旅行。

---

## 八、代价与边界

① 日志随版本增长，需要 checkpoint 控制重放长度。

② 删除向量堆积会拖慢查询，需要 OPTIMIZE。

③ 与 Spark 绑定最深，跨引擎要确认 connector 支持哪些特性。

④ VACUUM 会破坏时间旅行，设置保留期要权衡存储成本。

---

## 九、本篇小结

① Delta Lake 的元数据是 _delta_log，JSON 逐版本加 checkpoint 汇总。

② 读表靠重放日志得到当前文件列表。

③ 并发控制是乐观的，冲突检测看是否改了同一分区。

④ 删除向量让行级删除不必重写 Parquet，但要 OPTIMIZE 兜底。

⑤ 时间旅行按版本重放，VACUUM 会清除历史文件。
