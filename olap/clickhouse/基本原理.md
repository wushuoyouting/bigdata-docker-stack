# ClickHouse 基本原理

> **一句话结论**：ClickHouse 按列存储数据，用 MergeTree 组织不可变数据片段。它靠稀疏索引和向量化执行做单表扫描。本机采用单节点单容器，不引入 Keeper。

> **本文解决什么**：理解列存为何适合日志场景、数据片段如何生成与合并、单节点部署的依据。
>
> **适用谁**：准备安装 ClickHouse，或想知道命令背后机制的用户。
>
> **读完能做什么**：判断某张表该不该交给 ClickHouse，解释合并与变更的代价，读懂端口映射的依据。

## 一、列式存储

行式数据库把一行数据连续存放。列式数据库把一列数据连续存放。ClickHouse 属于后者。

每张表按列生成独立文件。同列数据类型一致，相邻值重复度高，压缩率随之提升。

查询只读取涉及的列。下面的语句只扫描 event_date 与 user_id 两列，不读取载荷列。

```sql
SELECT user_id, count()
FROM events
WHERE event_date = '2026-11-25'
GROUP BY user_id;
```

| 对比项 | 行式存储 | 列式存储 |
| --- | --- | --- |
| 连续存放单位 | 一行 | 一列 |
| 按列聚合 | 读取整行 | 只读目标列 |
| 压缩对象 | 混合类型 | 单一类型 |
| 适合场景 | 点查与事务 | 扫描与聚合 |

> 列存不擅长按主键取单行。该场景要读多个列文件，再拼回一行。

## 二、MergeTree 引擎

MergeTree 是 ClickHouse 的核心表引擎。它定义数据片段的排序、分区与合并方式。

INSERT 每写入一批数据，就生成一个不可变数据片段。片段内部按 ORDER BY 键升序排列。

| 子句 | 作用 | 是否必填 |
| --- | --- | --- |
| ORDER BY | 决定片段内排序与主键索引 | 是 |
| PARTITION BY | 决定分区目录，按分区独立合并 | 否 |
| PRIMARY KEY | 决定稀疏索引键，须为 ORDER BY 前缀 | 否 |
| SAMPLE BY | 决定抽样表达式 | 否 |
| TTL | 决定数据过期或迁移规则 | 否 |

下面建一张日志表。按月份分区，按日期与用户排序。

```sql
CREATE TABLE events
(
    event_date Date,
    user_id UInt64,
    event_type String,
    payload String
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_date)
ORDER BY (event_date, user_id);
```

> ORDER BY 不用于去重。它只决定磁盘顺序。重复键允许多行共存。

## 三、稀疏索引

MergeTree 的主键索引是稀疏索引。它不为每行建索引项，而为每批行建一个标记。

默认每 8192 行形成一个颗粒。颗粒是最小读取单位，由 index_granularity 控制。

| 索引类型 | 作用 | 建法 |
| --- | --- | --- |
| 主键稀疏索引 | 跳过不相关颗粒 | ORDER BY 自动生成 |
| minmax 跳数索引 | 按最小最大值跳读 | INDEX 加 TYPE minmax |
| set 跳数索引 | 按取值集合跳读 | INDEX 加 TYPE set |
| bloom_filter | 按存在性判断跳读 | INDEX 加 TYPE bloom_filter |

下面给高基数字段加跳数索引。四个颗粒合成一个索引块。

```sql
ALTER TABLE events ADD INDEX idx_user user_id TYPE bloom_filter GRANULARITY 4;
```

> 跳数索引只减少读取量。它不定位单行。索引块过大时，跳读收益下降。

## 四、查询执行路径

一条查询从接入到返回经历五个阶段。

① 客户端把 SQL 发到 HTTP 端口或原生端口。

② 服务端解析 SQL，生成抽象语法树。

③ 解释器把语法树转成处理管线。

④ 存储层按分区与索引定位颗粒，读取列文件。

⑤ 执行层按向量批量计算，把结果回传客户端。

```bash
curl -s 'http://localhost:8123/?query=SELECT%20count()%20FROM%20events'
```

预期输出一行数字。数字为 events 表的行数。

```sql
EXPLAIN SELECT count() FROM events WHERE event_date = '2026-11-25';
```

预期输出执行计划。计划中显示分区裁剪与索引使用情况。

| 阶段 | 产物 | 排查入口 |
| --- | --- | --- |
| 解析 | 抽象语法树 | 返回的错误行号 |
| 解释 | 处理管线 | EXPLAIN 输出 |
| 读取 | 列文件与颗粒 | system.parts |
| 计算 | 向量批次 | system.query_log |
| 返回 | 结果流 | 客户端超时设置 |

> 向量化执行一次处理一批值，不逐行调用。列存布局是向量化执行的前提。

## 五、写入与合并

写入不修改已有数据片段。新批次落成新片段，后台线程再把小片段合并成大片段。

片段过多会拉长查询耗时。每个分区的活跃片段数可在 system.parts 查看。

```sql
SELECT partition, count() AS parts
FROM system.parts
WHERE active AND database = 'default'
GROUP BY partition;
```

下面语句强制合并一个分区。该操作读写量大，只用于验证或维护窗口。

```sql
OPTIMIZE TABLE events PARTITION '202611' FINAL;
```

TTL 到期后，后台线程删除或搬迁数据。删除同样以片段为单位，不逐行擦除。

| 动作 | 实现方式 | 代价 |
| --- | --- | --- |
| INSERT | 生成新片段 | 片段数增加 |
| 后台合并 | 合并小片段 | 占用磁盘与输入输出带宽 |
| OPTIMIZE | 主动触发合并 | 短时资源占用高 |
| ALTER UPDATE | 重写受影响片段 | 异步执行，不适合频繁更新 |
| TTL 过期 | 删除或搬迁片段 | 后台执行 |

> 变更语句改写整块片段。频繁更新会让合并线程持续繁忙。该场景交给支持事务的数据库。

## 六、分片与副本

分片用于横向扩容。一张表的数据按键分散到多个分片。查询时各分片并行计算，再由发起节点汇总。

副本用于高可用。同一分片的多份数据保持一致。副本间通过 Keeper 传递操作日志。

| 角色 | 解决什么 | 依赖 |
| --- | --- | --- |
| 分片 | 容量与计算并行度 | 分片键与路由规则 |
| 副本 | 节点故障后的数据可用 | Keeper 与复制表引擎 |
| Keeper | 复制日志与分布式协调 | 独立进程或内置实现 |

ReplicatedMergeTree 必须配置 Keeper 地址。单节点不需要副本，因此也不需要 Keeper。

> 本机不部署 Keeper。引入 Keeper 只增加容器数量，不提升单节点验证价值。

## 七、适用边界

下表按数据形态与访问模式划分职责。Doris 与 StarRocks 是本仓库已有的分析型数据库。

| 场景 | 首选组件 | 原因 |
| --- | --- | --- |
| 日志与埋点明细 | ClickHouse | 追加写入，列存压缩率高 |
| 时序指标 | ClickHouse | 按时间分区，范围扫描快 |
| 超高基数单表 | ClickHouse | 跳数索引减少扫描量 |
| 多表关联分析 | Doris | 关联执行器更完整 |
| 高频点更新 | Doris | ClickHouse 变更代价高 |
| 湖格式联邦查询 | StarRocks | 湖 Catalog 支持更完整 |

> ClickHouse 不替代 Doris。两者在本机按场景并存。

## 八、部署取舍

单节点容器与分片副本集群的差异如下。

| 维度 | 单节点容器 | 分片副本集群 |
| --- | --- | --- |
| 容器数 | 1 | 多容器加 Keeper |
| 协调服务 | 无 | 必需 |
| 横向扩容 | 不支持 | 支持 |
| 故障切换 | 无 | 有 |
| 内存占用 | 低 | 高 |
| 适用场景 | 本机演示、SQL 调试 | 生产、海量数据 |

本机选单节点容器。16G 内存还要运行 Doris、MinIO 与其他组件。单节点省内存，也省掉 Keeper 配置。

> 从单节点迁到集群时，表结构加复制引擎与 Keeper 路径。查询 SQL 保持不变。

## 九、端口与协议

ClickHouse 提供两种客户端协议。HTTP 便于脚本与浏览器，原生协议便于命令行与高性能传输。

| 端口 | 协议 | 用途 | 暴露范围 |
| --- | --- | --- | --- |
| 8123 | HTTP | 查询接口与内置 Web UI | 宿主与同网络容器 |
| 9000 | 原生协议 | clickhouse-client 与驱动 | 同网络容器 |
| 9009 | 副本交换 | 副本间数据同步 | 容器内部 |
| 8443 | HTTPS | 加密查询接口 | 未启用 |

宿主 9000 已被 MinIO 占用。安装时把原生协议映射为宿主 19000。容器内仍监听 9000。

本机浏览器访问 http://localhost:8123。同网络容器访问 http://clickhouse:8123。写 localhost 会指向调用方自己。
