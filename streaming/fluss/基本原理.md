# 基本原理

本文解释 Fluss 的集群角色、表模型、存储结构与读写路径。适用于已完成安装并使用过 Flink SQL 的读者。读完能判断数据落在何处、故障如何恢复，以及如何按访问模式选型。

Fluss 是分布式流式存储系统。它把数据暴露为表，同时提供有序日志与键值存储。日志负责持续消费，键值存储负责更新与点查。远端文件系统与开放表格式负责恢复和历史访问。

## 一、集群角色

Fluss 把协调与数据服务分离。控制面由 CoordinatorServer 承担，数据面由 TabletServer 承担。客户端发现节点后直接与 TabletServer 通信，从而把数据流量与协调负载分开。

| 角色 | 职责 |
| --- | --- |
| CoordinatorServer | 管理库、表、分区、节点成员与桶副本分配 |
| TabletServer | 承载桶副本，处理读写，复制日志，执行后台任务 |
| ZooKeeper | 保存集群元数据，支撑节点注册与协调器选主 |
| 远端存储 | 保存分层日志段与键值快照 |
| 客户端与连接器 | 发现元数据，路由请求，向计算引擎暴露表操作 |
| Fluss Gateway | 提供无状态 HTTP 入口，处理元数据、DDL 与批量写入 |
| 湖仓分层服务 | 以独立 Flink 作业维护表的开放湖格式表示 |

### 1.1 协调器

CoordinatorServer 维护元数据并决定数据放置。它创建与修改库表分区，跟踪可用 TabletServer，分配桶副本并维护领导权。扩容缩容时，它协调副本重分配与再均衡。

多个 CoordinatorServer 可同时部署。它们借助 ZooKeeper 选出一个活跃节点，其余作为 standby。领导权切换时用协调器纪元标记新 leader，并阻止旧 leader 的过期操作。

协调器故障主要影响管理操作。已有读写可由健康的 TabletServer 继续服务。

### 1.2 数据服务节点

TabletServer 构成数据服务层。它处理所承载桶的请求。它管理本地日志与键值文件。它还执行日志复制、快照与上传等后台任务。

每个桶有一个 leader 与若干 follower 副本。leader 服务写入，follower 拉取日志。一台 TabletServer 通常承载多个桶，对部分桶是 leader，对其余桶是 follower。

## 二、数据模型

### 2.1 逻辑层级

Fluss 用四层抽象组织数据。层级关系如下。

```
Database
  └── Table
        └── Partition（可选）
              └── 一个或多个 Bucket
```

表定义列名、类型、表类型与存储属性。库是表的命名空间。分区按列值把行分组管理，每个分区有独立的桶。

### 2.2 桶与分片

桶是数据分布、日志排序与副本分配的单位。非分区表只有一组桶。分片是桶在某台 TabletServer 上的存储表示。

排序只在桶内保证。不同桶的记录可并发处理。应用不能假设全表有序。需要相关事件进入同一桶时，应定义合适的哈希桶键。

### 2.3 两类表

主键的有无决定表类型。两者的差异如下。

| 项 | 日志表 | 主键表 |
| --- | --- | --- |
| 行标识 | 每次追加生成新记录 | 主键标识一行 |
| 写入方式 | 仅追加 | 插入、更新与删除 |
| 重复值 | 保留为多条记录 | 按合并引擎处理 |
| 典型读取 | 按桶偏移消费与重放 | 按键点查与消费变更 |
| 存储内容 | 有序日志 | 当前键值状态加变更日志 |
| 典型用途 | 事件流、活动流、采集日志 | 实体状态、维表、汇总结果 |

### 2.4 键约束

主键表有三类键。约束如下。

| 键 | 用途 | 主键表约束 |
| --- | --- | --- |
| 主键 | 定义行标识与更新目标 | 必须包含全部分区列 |
| 分区键 | 决定行所在分区 | 必须是主键的子集 |
| 桶键 | 把行哈希到桶 | 必须是主键子集且不含分区列 |

主键表未显式指定桶键时，默认用去掉分区列后的主键。哈希分桶保证同一键的操作落入同一桶。

## 三、存储引擎

### 3.1 日志存储

LogStore 为每个桶维护追加序列。记录带偏移量，读者用偏移量跟踪进度或恢复消费。日志在本地磁盘上按段组织，较旧的段可上传到远端存储。

Fluss 默认用 Apache Arrow 作为日志格式。列式批次支持压缩与列裁剪，适合分析型读取。另有 COMPACTED 行式编码可选。格式只决定表示方式，不改变表语义。

日志表把追加数据写入日志。主键表把处理写入时产生的变更写入日志。两类表共用这套日志结构。

### 3.2 键值存储

KvStore 维护主键表的当前行状态，底层用 RocksDB。它支持按键访问。写入如何处理由表配置决定。选项有三个：覆盖整行、更新指定列、使用其他合并引擎。

合并引擎决定同一主键再次出现时如何处理。四种引擎如下。

| 引擎 | 行为 | 适用场景 |
| --- | --- | --- |
| LastRow | 采用最后一次写入 | 订单与画像状态 |
| FirstRow | 保留该键首条记录 | 事件标识去重 |
| Versioned | 按版本列接受更新 | 乱序实体更新 |
| Aggregation | 按列配置聚合函数 | 计数器与汇总结果 |

默认行为按写入处理顺序生效，不自动选择事件时间最大的记录。变更镜像是独立选择：FULL 包含更新前后记录，WAL 省略更新前记录。

## 四、读写路径

### 4.1 发现与路由

客户端从配置的 bootstrap servers 开始。它先发现集群元数据。接着解析目标表与桶所在的节点，再用元数据路由请求。领导权或节点状态变化时，客户端刷新元数据。

客户端必须能访问集群通告的地址。仅 bootstrap 入口可达并不足够。若 TabletServer 地址从应用网络不可达，读写同样失败。

### 4.2 写入日志表

客户端先选择桶，再批量发送记录到桶 leader。leader 把批次追加到本地日志，follower 拉取新记录。写入完成取决于客户端的确认设置。

### 4.3 写入主键表

客户端按键把插入或删除路由到桶。leader 按表的合并规则处理写入，把结果变更记入日志，再更新键值状态。复制日志提供重建状态所需的历史。

确认由复制要求决定。键值快照上传是独立的后台操作，不阻塞写入链路。

### 4.4 读取方式

Fluss 提供多种访问路径。说明如下。

| 方式 | 行为 |
| --- | --- |
| 日志扫描 | 从指定偏移读记录，可持续消费新数据 |
| 主键点查 | 按键路由，从当前键值状态取行 |
| 快照扫描 | 读主键快照，并记录后续消费的日志位置 |
| 远端日志读 | 读取已从本地卸载但仍保留的日志数据 |
| 联合读取 | 合并已提交的湖端数据与相关 Fluss 数据 |

日志消费者读到桶的高水位线为止。高水位线是已提交日志的边界，随复制进度前进。主键桶的高水位线还与键值状态更新协调。各桶独立推进。

## 五、分层存储

### 5.1 三层结构

数据按访问温度分布在三层。说明如下。

| 层 | 内容 | 作用 |
| --- | --- | --- |
| 本地存储 | 近期日志段、活跃键值状态 | 提供低延迟读写 |
| 远端存储 | 分层日志段、键值快照 | 支持恢复与历史回放 |
| 湖仓层 | 开放表格式数据 | 支持历史分析与批读 |

远端存储如 S3 或 HDFS。异步上传意味着远端存储不替代新写入记录的副本机制。上传日志到对象存储不会自动生成 Iceberg 或 Paimon 表。

### 5.2 湖仓分层

开启湖仓分层后，独立 Flink 作业负责沉降。该作业增量读取 Fluss 数据，写入开放表格式。它提交变更，并把进度记录回 Fluss。该进度把湖表示与 Fluss 日志位置关联起来。

兼容的读取方用联合读取合并已提交的湖数据与相关 Fluss 数据。直接读湖表的引擎看到的是已提交表示，新鲜度取决于分层进度。

### 5.3 生命周期

四类保留策略彼此独立。说明如下。

| 参数 | 控制对象 |
| --- | --- |
| table.log.ttl | 日志表记录或主键变更日志的保留期 |
| table.log.local-ttl | 上传远端后本地日志副本的清理时间 |
| table.log.tiered.local-segments | 上传后本地保留的日志段数 |
| table.kv.ttl | 主键表单行状态的过期时间 |

过期与清理异步执行。键值过期不向变更流发删除事件。本地日志清理同时受时间与段数约束。仅设置本地 TTL，不保证每条记录都保留到该时长。

## 六、复制与恢复

### 6.1 写入持久性

Fluss 按表的副本因子复制每个桶的日志。leader 维护同步副本集。三个关键设置如下。

| 设置 | 作用 |
| --- | --- |
| table.replication.factor | 决定桶日志的副本数 |
| client.writer.acks | 决定写入等待谁确认 |
| log.replica.min-in-sync-replicas-number | acks=all 时要求的最少同步副本数 |

acks=all 等待的是同步副本，不是全部已配置副本。同步副本数不满足下限时写入失败。副本应跨故障域放置。

### 6.2 故障恢复

TabletServer 故障时，协调器调整受影响桶的领导权与副本。客户端刷新元数据并向当前 leader 重试。主键桶的新 leader 必须先准备好键值状态才能服务。

正常恢复路径是加载已完成的远端快照，再从快照记录的偏移重放日志。没有快照时，恢复依赖所需的日志历史仍可访问。快照时间、日志保留量与存储带宽共同决定恢复时长。
